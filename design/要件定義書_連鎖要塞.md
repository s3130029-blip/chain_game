# 要件定義書：非同期・連鎖コンボ対戦ゲーム

> ワーキングタイトル：**連鎖要塞 / CASCADE**（仮。後述の通り名前は最後でよい）
>
> 目的：「キングオブワンズの移動連鎖コンボ」と「激突要塞！の非同期共有対戦」を融合し、**操作技術ではなく構築力で勝負する**ブラウザゲームを、GitHub Pages 上のサーバーレス構成で個人開発する。
>
> このドキュメントは設計判断と根拠をまとめたもので、コードは含みません。

---

## 0. 結論サマリー（最初に読む）

- **コア体験は成立する。** 「設計して走らせる」遊び（Super Auto Pets / Into the Breach / Zachtronics 系）と「作品を共有して非同期で戦わせる」遊び（激突要塞！/ Super Auto Pets）は、どちらも単体で実証済み。融合は有望。
- **ただし成否は実装に強く依存する。** 特に「①連鎖が見ていて気持ちいいか」「②受け身の観戦にならないか」「③対戦相手がいない初期（コールドスタート）をどう乗り切るか」の3点が勝負。
- **GitHub Pages だけで MVP は実現可能。** 決定論的シミュレータをクライアント側で完結させ、盤面を文字列にエンコードした「共有コード」で非同期対戦する構成なら、ログイン不要・インストール不要・サーバー不要で成立する。
- **ランキング/作品ギャラリー/マッチングはサーバーが要る** ので、MVP では割り切って後回し（Firebase フェーズ）。
- **最初の3か月の優先順位：1か月目はエンジン（戦闘シミュレータ）だけを作って「面白いか」を検証。** UI は2か月目。3か月目で調整と共有導線。

## 1. このゲームのコア体験は何か

一言でいうと：

> **「位置と順番を設計し、ドミノのように連鎖する盤面を組み上げ、それを他人の盤面とぶつけて結果を見る」**

分解すると、プレイヤーが本当に楽しむ瞬間は次の3つです。

1. **設計の快楽（キングオブワンズ由来）**
   ユニットそのものの強さではなく、「どこに置くか」「どの順で動くか」「押し出した先で何が起きるか」を考える。1つの行動が次を呼び、さらに次を呼ぶ連鎖を“仕込む”面白さ。

2. **解明・予測の快楽（連鎖システム由来）**
   ルールが決定論的だからこそ、「この配置ならこう転がるはず」と頭の中でシミュレートできる。読み通りに連鎖が決まると脳が喜ぶ。Zachtronics 系や詰将棋に近い満足。

3. **共有と競争の快楽（激突要塞！由来）**
   自分の“作品”をコード化して人に渡す。相手の作品と非同期で戦わせ、勝敗を見る。「誰の構築が最強か」をSNSで競う。リアルタイムの反射神経は不要。

重要なのは、**プレイヤーの主体性が「操作」から「設計」へ移っている**こと。プレイヤーは小さなプログラム（配置＋ルール）を書き、それを走らせて結果を見る。これがこのゲームの背骨です。

## 2. 本当に面白くなるか（正直な評価）

### 面白くなる根拠
- **設計＝遊び** は近年の人気ジャンル（Super Auto Pets、Into the Breach、Wildfrost、Zachtronics 諸作）で繰り返し実証されている。
- **非同期オートバトル＋共有** は Super Auto Pets が大ヒットで証明済み。激突要塞！の文化自体が「これは面白い」の生き証人。
- あなたの嗜好（収集要素やレア度に興味がない／配置と挙動を考えるのが好き）は、このジャンルの“コア層”の嗜好と完全に一致している。作り手が本質的なファンであることは強い。

### 正直に言う「面白くならないかもしれない」リスク
ここは遠慮なく指摘します。

- **観戦が受け身になる問題（最大のリスク）**
  「コードを貼って、自動戦闘を眺めて、勝敗を見る」だけだと、プレイヤーが“遊んでいる”感覚を失いやすい。眺めるだけの時間が長いと飽きる。
  → 対策は §11 に詳述しますが、要点は「**設計フェーズを深く・楽しくする**」「**負けたら相手をどう崩すか考える“カウンター構築”のループを作る**」「**リプレイは短く・派手に**」。

- **連鎖が“読めるが浅い”or“派手だが理不尽”に振れる問題**
  決定論を強くしすぎると最適解が一つに収束して(=meta が解かれて)飽きる。ランダムを入れすぎると非同期対戦で理不尽になり、設計の意味が薄れる。バランスの綱渡り。
  → MVP は **完全決定論**を推奨（設計と予測こそ売りなので）。飽き対策は「ユニット追加」「マップの非対称性」で後から足す。

- **連鎖そのものが気持ちよくない可能性**
  これは作ってみないと分からない、最大の不確実性。だから §14 で「**1か月目はエンジンだけ作って、紙とコンソールで連鎖の手応えを検証する**」ことを最優先に置いています。ここが面白くなければ、UI をどれだけ磨いても救えません。

### 総合評価
**「コンセプトは有望。ただし“エンジンのプロトタイプが面白いか”が分水嶺。」** ここを最初に検証すれば、無駄な作り込みを避けられます。

## 3. 類似ゲームとの比較

| ゲーム | 共通点 | あなたの企画との決定的な違い（＝差別化ポイント） |
|---|---|---|
| **Super Auto Pets** | 非同期オートバトル、構築を共有、ログイン軽め | あちらは横一列のステータス殴り合いが中心。**こちらは盤面上の「移動・押し出し・位置関係」で連鎖する**点が新しい |
| **Into the Breach** | 押し出し・位置取りの連鎖、決定論的、読みの面白さ | あちらは1人用パズル＋リアルタイムの手番入力。**こちらは非同期PvPで“設計を共有して戦わせる”** |
| **オートチェス系（TFT等）** | オートバトル＋配置 | あちらはリアルタイム・マッチング前提でサーバー必須。**こちらは共有コードでサーバーレス非同期** |
| **激突要塞！** | パスワード共有、非同期で他人の作品と対戦 | 当時は掲示板＋手作業。**こちらはSNS時代の摩擦のない共有とリプレイ文化に最適化** |
| **Zachtronics系 / Baba Is You** | 「仕組みを設計して走らせる/ルールを操作する」遊び | 対戦要素は薄い。**こちらは“設計を競い合う非同期PvP”に振っている** |
| **キングオブワンズ** | 移動連鎖コンボ、Kingを守る | リアルタイム操作中心。**こちらは“操作を排し、設計と非同期共有に純化”** |

差別化を一文で言うと：

> **「Into the Breach 的な位置連鎖を、Super Auto Pets 的な共有コード非同期対戦に載せ、激突要塞！のSNS共有文化で回す」** ——この三点交差に既存タイトルはいません。

そして本企画の本質は「キングオブワンズの再現」ではなく、**“あの設計の快感”を、現代の非同期共有・低摩擦・リプレイ共有という器に作り直すこと**です。

## 4. 個人開発として実現可能か（GitHub Pages 判定）

判定基準＝「GitHub Pages 上で実現できるか」で各要素を仕分けます。

| 要素 | GitHub Pages（静的）だけで可能？ | 補足 |
|---|---|---|
| 盤面エディタ（ユニット配置） | ✅ 可能 | 純粋にクライアント側の状態管理 |
| 戦闘シミュレータ（自動進行・連鎖） | ✅ 可能 | **決定論にすればクライアント完結。これが鍵** |
| リプレイ再生（連鎖の可視化） | ✅ 可能 | シミュレータが出力したイベントログを再生するだけ |
| 共有コード（盤面の文字列化） | ✅ 可能 | 盤面JSON→圧縮→Base64。サーバー不要 |
| 共有コードで対戦 | ✅ 可能 | 相手コードを貼る→復号→同じシミュレータで走らせる |
| ログイン不要 / インストール不要 | ✅ 可能 | 完全静的サイト |
| スマホ/PCブラウザ対応 | ✅ 可能 | レスポンシブ設計で対応 |
| オンラインランキング | ❌ 不可（要外部サービス） | Firebase 等が必要 → **後回し** |
| 作品ギャラリー / 投稿機能 | ❌ 不可（要DB） | 同上 → 後回し |
| 自動マッチング | ❌ 不可（要サーバー） | 非同期＋共有コードなら**そもそも不要** |

**結論：MVP のすべてが GitHub Pages の静的ホスティングだけで成立します。** サーバーが要るのは「中央集権的な発見・ランキング」だけで、それは非同期＋共有コードという設計を選んだ時点で MVP からは外してよい部分です。

#### 推奨技術スタック（最小）
- **言語：TypeScript** を推奨。ユニットやイベントの型が複雑になるので、型安全が効く。ビルドなしで始めたいなら素のJSでも可。
- **ビルド：Vite**（`vite build` で静的ファイルを出力 → GitHub Pages へ）。ビルド工程を避けたいなら単一HTML＋ESモジュールでも動く。
- **描画：MVPは DOM＋CSS Grid で十分**（小さな盤面なら）。連鎖アニメが重くなったら Canvas（または PixiJS のような軽量ライブラリ）へ移行。
- **共有コード圧縮：LZ-string** 等。短くしてSNSに貼れる長さに。
- **フレームワーク：不要**（必要なら Preact のような極小のもの）。
- **決定論の担保：`Math.random()` をシミュレータ内で使わない**。乱数が要る場合はシード付き擬似乱数を自作し、シードを共有コードに含める。

## 5. MVP（最小実装版）の提案

「これだけあればコアループが回る」最小セット。**足したくなっても足さない**ことが重要です。

**MVP に含むもの**
1. 決定論的な戦闘シミュレータ（エンジン）
2. ユニット種類：**6種程度**（連鎖が組める“役割の違う”最小セット）
3. 盤面エディタ（配置ゾーンにユニットを置く、スマホ対応）
4. リプレイビューア（連鎖が分かるアニメ再生・スキップ可）
5. 共有コードの生成／読み込み（貼り付けて対戦）
6. **開発者が作り込んだ「道場（ガントレット）」相手 5〜10体**（対戦相手ゼロでも遊べる＝コールドスタート対策＆チュートリアル兼用）
7. 戦闘結果のシェア（コードのコピー、Wordle 風の結果テキスト）

**MVP に含まないもの（明確に後回し）**
- ランキング、作品ギャラリー、ユーザー投稿、アカウント、リアルタイム通信、課金、収集要素、デッキ大量管理、凝った演出。

**MVP のゴール定義**
「友人数人に共有コードを渡したら、相手の構築を崩すために配置を考え直して再挑戦する」——この**カウンター構築のループが自然に発生したら成功**。

## 6. ゲームループの設計

### マクロループ（プレイヤーの周回行動）
1. **構築**：ユニットを配置し、連鎖を仕込む
2. **テスト**：手元の道場相手やセーブした自分の旧構築と戦わせ、挙動を確認
3. **共有**：完成した構築を共有コードにしてSNS/友人へ
4. **対戦**：他人のコードを読み込み、自動戦闘のリプレイを見る
5. **分析・カウンター**：負けた相手をどう崩すか考え、§1 の構築へ戻る

このループの肝は **2（テスト）と 5（カウンター）**。ここが回るほど“設計し続ける”遊びになります。

### ミクロループ（1戦の中）
1. 両者の盤面をロード（自分＝編集中、相手＝共有コード）
2. ターン制で進行。各ターン、いずれかのユニットが「行動」する
3. その行動が他ユニットの「反応（トリガー）」を誘発 → **連鎖（カスケード）が最後まで解決**
4. 連鎖が収まったら次のユニットの番
5. 勝敗条件を満たすか、規定ターンに達したら終了 → 結果表示

## 7. 勝敗条件の設計

両ソースゲームを綺麗に繋ぐ装置として、**各陣営に「コア」を1つ持たせる**ことを提案します。

- キングオブワンズ＝守るべき「King」
- 激突要塞！＝守るべき「要塞」
- → 本作＝守るべき **コア（核 / Core）**

コアがあることで、連鎖は「ただ派手」ではなく **「相手のコアまで届かせる手段」** という目的を持ちます。これがゲームを締めます。

**勝利条件（優先順）**
1. **相手のコアを破壊する**（押し出して盤外＝撃破、または直接ダメージで撃破）
2. 規定ターン経過時、**生存ユニット数 → 残コアHP → 合計残HP** の順で判定
3. 同点なら引き分け（非同期では「攻め有利/守り有利」の偏りを避けるため、引き分け扱いは初期は許容）

**設計上の注意（非同期特有）**
- 先攻後攻の有利不利が大きいと、同じ2構築でも順番で勝者が変わってしまう。**「両方の順番で戦わせ、2戦の合計で判定」**するなどして、攻守の非対称を均すことを検討（実装は軽い）。
- “守り切れば勝ち”だけにすると超防御構築が支配的になりがち。**ターン経過で盤面が狭まる/中央にダメージ床が出る**等の「決着を促すルール」を入れて、千日手・引き分け量産を防ぐ。

## 8. ユニット設計方針

### 原則
- **収集ではなく組み合わせ。** 全ユニットは初期から全員に解放。レア度なし。
- **少数の“役割の違う”プリミティブ**で、組み合わせ爆発を生む。MVP は6種程度。
- 各ユニットは「数値の強さ」より **「連鎖にどう寄与するか（押す・引く・誘発する）」** で差別化する。

### ユニットのデータスキーマ（実装イメージ）
各ユニットは概ね次の属性を持ちます（擬似スキーマ）。

```
Unit {
  type:      string         // 種類ID
  hp:        number
  speed:     number         // 行動順（初期値の決定論的な並び替えに使う）
  move:      MovePattern    // 例: 前進1 / 最寄りの敵へ1歩 / 不動
  push:      PushBehavior   // 例: 衝突したユニットを1マス押す / 押さない
  trigger:   { on: Event, do: Effect }[]   // ← 連鎖の核
  facing?:   Direction      // 向き（押し出し方向などに影響）
}
```

`trigger` の `Event`（誘発条件）と `Effect`（効果）の組み合わせが、連鎖のすべてを生みます。

- **Event 例**：出撃時 / 移動した時 / 何かを押した時 / 押された時 / 衝突した時 / 隣に敵が来た時 / 味方が倒れた時 / 自分が倒れた時
- **Effect 例**：対象を押す / 引き寄せる / ダメージ / 自分が移動 / 位置を入れ替える / 周囲のユニットの trigger を誘発 / 一定方向へ吹き飛ばす

### MVP の6種（叩き台・要調整）
1. **プッシャー**：衝突した相手を1マス押す。連鎖の起点。
2. **リアクター**：押されると、進行方向の延長線上にいる相手をさらに押す（＝連鎖を“伝播”させる）。
3. **ボマー**：自分が倒れる/押し出された時、周囲4マスを吹き飛ばす（爆発で連鎖を拡散）。
4. **マグネット**：自ターンに最寄りの敵を1マス引き寄せる（位置関係を能動的に作る）。
5. **スワッパー**：隣の敵と位置を入れ替える（陣形を崩す/相手を危険地帯へ運ぶ）。
6. **コア（核）**：移動しない。守る対象。撃破されたら負け。

この6種だけでも「プッシャーで押す→リアクターが伝播→ボマーに当たって爆発→相手コアが盤外へ」のような連鎖が組めます。**まずこの“最小で連鎖が成立するセット”を engine で検証**してください。

### バランス方針
- **強い数値**ではなく**便利な接続**を作る。1体だけで完結する強ユニットを避ける（コンボ前提に寄せる）。
- 決定論なので**全数テストに近いことが可能**。支配的な組み合わせ（壊れコンボ）が見つかったら、その接続を弱める/コスト化する。
- 配置に**コスト/枠の上限**（例：合計コスト◯まで、◯体まで）を設けて、強い組み合わせの無制限投入を防ぐ。

## 9. 連鎖システム設計（最重要・最も実装注意）

ここがゲームの心臓です。**自動戦闘なのに連鎖が起きる**ためには、「プレイヤーが仕込んだルール（トリガー）」が連鎖を生む仕組みが要ります。

### 採用モデル：「トリガー＆カスケード（解決を尽くす）」
- ターンが来たユニットが**1つの行動**を起こす（起点＝スパーク）。
- その行動が他ユニットの `trigger` を誘発し、誘発された効果がさらに別の `trigger` を誘発する。
- **連鎖が完全に収束するまで解決してから**、次のユニットの番に進む。
- これにより「1手が雪崩を打つ」ドミノ感が最大化されます（キングオブワンズの快感の再現）。

### 決定論を守るための“解決順”ルール（実装の肝）
非同期対戦と再現可能リプレイのため、**乱数を使わず、曖昧さを排除**します。最低限、次を固定で定義してください。

1. **行動順（イニシアチブ）**：`speed` 降順。同値は盤面の読み順（例：上→下、左→右）で決定。
2. **連鎖の解決順**：誘発された反応はキュー（FIFO）に積み、積まれた順に処理。同時誘発は同じ読み順で並べる。
3. **衝突・押し出しの解決**：押した先にユニットがいれば「押し連鎖」を再帰的に解決。盤外に出たら撃破。
4. **無限ループ防止**：1ターン内の連鎖ステップ数に上限（例：200ステップ）を設け、超過したら強制終了。相互に押し合う構成での暴走を防ぐ。
5. **同時消滅などの端ケース**：必ずルールを明文化（例：HP0は連鎖ステップの境界でまとめて除去）。

> このルール表が **そのままテスト仕様**になります。曖昧な箇所を残すと、同じ2コードでも環境で結果がブレ、非同期対戦が破綻します。最初にここを書き切ることが品質の8割です。

### リプレイ＝イベントログ方式
- シミュレータは「何が起きたか」を**イベントの配列**として出力する（例：`{t, kind:'push', from, to, dir}` の列）。
- 画面はこのログを順に再生するだけ。**シミュレーション本体と描画を分離**することで、(a) ヘッドレスにテストでき、(b) 共有コード2つだけからリプレイを完全再現でき、(c) スキップ/早送りが楽になります。

### 連鎖を“気持ちよく見せる”ための演出指針（後で効く）
- 連鎖が深くなるほど**テンポを少し上げ、音とエフェクトを盛る**（コンボ数表示、画面シェイク）。
- 1戦は**短く**（数十秒以内が理想）。長いと観戦の退屈リスク（§2）が顕在化する。
- 「**ここが効いた**」が一目で分かるよう、決め手の瞬間をハイライト。

---

## 10. 共有コードシステム設計

激突要塞！の“パスワード文化”の現代版。**完全にサーバーレスで成立**します。

### 仕組み
1. 盤面の状態（盤サイズ、各ユニットの種類・座標・向き、コア、ルールバージョン、必要ならシード）を **JSON 化**。
2. それを **圧縮**（LZ-string 等）して **Base64（URLセーフ）** に。
3. 出来た文字列が「共有コード」。コピーしてSNS/DM/掲示板に貼れる。
4. 対戦側はコードを貼る → 復号 → 同じシミュレータで走らせる。**サーバー一切不要。**

### フォーマット設計の注意
- **必ず先頭にバージョン番号**を入れる（例：`v1:...`）。ルールやユニットを更新した時、旧コードの扱い（再現/非対応の明示）を制御できる。
- **短さを意識**。盤が小さければ数十〜200文字程度に収まる。長すぎるとSNSで貼りづらい。
- **改ざん耐性は MVP では不要**だが、軽いチェックサムを付けると破損コードを弾けて親切。
- **URL 埋め込み対応**：`https://<your>.github.io/?b=<コード>` でリンク一発共有できると体験が劇的に良くなる（クリック→そのまま対戦画面）。これは静的サイトでも可能なので、MVP に入れる価値が高い。

### 結果の共有（Wordle 方式）
- 戦闘後、**ネタバレしすぎない短い結果テキスト**を生成（例：勝敗、最大連鎖数、決め手の絵文字グリッド等）。
- 「この結果を再現するコードはこちら」と添えてSNS拡散を促す。**“結果が共有したくなる”ことがバズの起点**になります（Wordle が証明）。

---

## 11. コミュニティが盛り上がる仕組み

非同期共有ゲームは「**対戦相手＝コンテンツ**」です。人の作品が回らないと過疎ります。MVP（サーバーなし）でも回す工夫：

- **道場（ガントレット）を最初から充実させる**：開発者製の段階的な相手 5〜10体。対戦相手ゼロでも遊べ、チュートリアルも兼ねる。**コールドスタート最大の対策。**
- **“崩したくなる”名物構築を仕込む**：強くてクセのある相手を置き、SNSで「こいつ倒せた？」が起きる構造を作る。
- **URL一発共有 ＋ 結果シェア**（§10）で摩擦を限界まで下げる。
- **「お題」運用**：あなたが運営として「今週のレギュレーション：プッシャー禁止」等を出題し、ハッシュタグで投稿を集める。サーバーなしでも“イベント”は回せる。
- **カウンター構築の可視化**：負けた後に「相手のコードを編集して試す」導線を置くと、設計し続ける動機（＝§2の受け身対策）になる。
- **（後の Firebase フェーズで）週間ランキング・作品ギャラリー・いいね**。ただし**コミュニティの熱は機能より“崩したくなる相手”が作る**ので、MVP では中身（相手構築の質）に投資する。

---

## 12. 長期的な拡張案

MVP が当たってから、段階的に。

- **Firebase フェーズ**：作品ギャラリー、週間ランキング、いいね/ブックマーク。共有コードはそのまま「投稿の中身」になるので移行が滑らか。
- **リーグ/シーズン制**：定期的に環境（使えるユニット）が変わり、meta が更新され続ける（決定論ゆえの“解かれて飽きる”対策）。
- **ユニット追加とマップ多様化**：新トリガー、ダメージ床、ワープ、壁など。連鎖の“地形パズル”性を深める。
- **トーナメント/総当たり**：投稿された構築を自動総当たりさせ、王者を決める（激突要塞！の“最強決定戦”の正統進化）。
- **構築の“フォーク”文化**：他人のコードを土台に改造して再投稿（GitHub的な発想で、開発者であるあなたと相性が良い）。
- **観戦・解説モード**：注目の対戦をピックアップ、決め手を解説。eスポーツ的な見せ場。
- **モバイルアプリ化やエディタ強化**は、Web で需要が確認できてから。

## 13. リスクとアンチパターン（総まとめ）

| リスク | 深刻度 | 対策 |
|---|---|---|
| 連鎖が気持ちよくない | 致命 | **1か月目にエンジンだけで検証**。ダメなら設計を見直す（UIに進む前に） |
| 観戦が受け身で飽きる | 高 | 設計フェーズを濃く／カウンター構築ループ／リプレイは短く派手 |
| 対戦相手がいない（コールドスタート） | 高 | 道場相手を充実／URL・結果シェアで摩擦削減／お題運用 |
| meta が解かれて飽きる（決定論ゆえ） | 中 | 定期的なユニット追加・レギュレーション・シーズン制 |
| バランス崩壊（壊れコンボ） | 中 | ユニット少数＋コスト上限＋決定論ゆえの全数テスト |
| 先攻後攻の非対称で結果がブレる | 中 | 攻守入替の2戦合計で判定するなど |
| 共有コードの後方互換崩れ | 中 | 先頭にバージョン番号、更新時の方針を明示 |
| スコープ膨張（ユニット/機能の足しすぎ） | 中 | MVP定義を死守。足したくなったら“後回しリスト”へ |
| 連鎖の無限ループで処理暴走 | 低〜中 | 1ターンの連鎖ステップ数に上限 |

**避けるべきアンチパターン**：先にUI/演出を作り込む、ユニットを最初から大量に入れる、ランキング等のサーバー機能を MVP に入れる、決定論ルールを曖昧なまま実装する。

## 14. 個人開発者が最初の3か月で作るべき範囲

方針：**「エンジン → UI → 仕上げ・共有導線」の順。最初の1か月で“面白いか”を判定する。**

### 1か月目：エンジン（戦闘シミュレータ）だけ。UIなし。
> ゴール：**画面なしでも「連鎖が面白いか」を判定できる状態**にする。ここで面白くなければ立ち止まる。

- **Week 1**：データモデル（Unit / 盤面 / ターン）、基本移動、行動順（決定論）。
- **Week 2**：押し出し・衝突の再帰解決、**トリガー（誘発）システム**の骨格。
- **Week 3**：ユニット **6種** 実装、勝敗条件、ヘッドレスで1戦を最後まで走らせる（コンソールに連鎖ログ出力）。
- **Week 4**：**イベントログ方式**で連鎖を記録（後の再生用）。決定論ルール（§9）の端ケースを潰す。
  - ✅ **この時点で、手で2つの盤面を作って戦わせ、連鎖ログを読んで「ニヤッとするか」を自己検証する。** ここが Go / No-Go。

### 2か月目：UI（エディタ・リプレイ・共有コード）
> ゴール：**人に共有コードを渡して非同期対戦できる**最小プロダクト。

- **Week 5**：盤面エディタ（タップ/クリックで配置、スマホ対応）。
- **Week 6**：リプレイビューア（イベントログを再生、連鎖が分かる演出、スキップ可）。**ここが“面白さを売る”画面**。
- **Week 7**：共有コードの生成/読込、**URL埋め込み共有**、相手コードを貼って対戦。
- **Week 8**：**道場相手 5〜10体**を作成、最小チュートリアル（最初の連鎖を体験させる）。

### 3か月目：仕上げ・調整・拡散の種まき
> ゴール：**友人に渡して“カウンター構築のループ”が回る**ことを確認し、公開する。

- **Week 9–10**：バランス調整（決定論ゆえテスト容易）、支配的コンボの是正、**結果シェア（Wordle方式）**実装。
- **Week 11**：友人とプレイテスト、スマホ最適化、演出の“ジュース”（連鎖時の音・シェイク・コンボ表示）。
- **Week 12**：**GitHub Pages へデプロイ**、遊び方ページ、SNSで作例コードと一緒に公開してコミュニティの種をまく。

### 3か月後に「できているもの」
- GitHub Pages で動く、ログイン不要・インストール不要・スマホ/PC対応のブラウザゲーム。
- 6種のユニットで連鎖を組む盤面エディタ、決定論的オートバトル、連鎖が分かるリプレイ。
- 共有コード（URL一発共有・結果シェア付き）による非同期対戦。
- 対戦相手ゼロでも遊べる道場相手。

### 3か月後に「まだ無いもの（次フェーズ）」
- ランキング、作品ギャラリー、投稿機能、アカウント（＝Firebase フェーズ）。
- 大量のユニット、シーズン制、トーナメント自動化。

## 付録：用語

- **コア（核 / Core）**：各陣営が守る不動ユニット。撃破で敗北。両ソースゲームの「King」「要塞」の役割。
- **トリガー（Trigger）**：「ある出来事（Event）が起きたら、ある効果（Effect）を発動する」というユニットの反応ルール。連鎖の素。
- **カスケード（Cascade）**：1つの行動が次々とトリガーを誘発し、連続的に解決される連鎖。
- **共有コード**：盤面状態を圧縮・文字列化したもの。これを渡すだけで非同期対戦が成立する。
- **道場（ガントレット）**：開発者が用意した対戦相手群。コールドスタート対策＆チュートリアル。
- **決定論的（Deterministic）**：同じ入力からは必ず同じ結果になる性質。非同期対戦の公平性とリプレイ再現の前提。
